# Implementation Plan — Pokémon Pack Battle: RIP packs + unlocked collection (04.3)

> **Checkpoint protocol** (from `02-tron-game-plan.md` + `05-agent-discipline.md`): run ONE checkpoint
> per session turn. After each checkpoint run the narrowest relevant validation (`npm run build`,
> plus `npm run lint` for code), report *files + behaviour + result*, then STOP and wait for "next".
> No checkpoint may quietly widen its own Do-NOT list.
>
> **Sub-step protocol (CP5 onward, mirroring 04.1's TASK format):** every checkpoint with multiple
> distinct surfaces is split into sub-steps (`CP5-A`, `CP5-B`, ...) so no single pass carries a whole
> feature. Each sub-step states **Files / Inputs / Logic / Do-NOT / Gate**. Run ONE sub-step per
> session turn, validate, report, then STOP.
>
> **Scope:** a new solo feature inside `pokemon-pack-battle` (game 04) only. No P2P protocol change,
> no new assets, no new highscore bucket. It adds two new **session views** (`rip` and `unlocked`),
> one new **persisted bucket** `openedCards` (per-player card-id sets), one new co-located component
> (`PokemonPackRip`), and the integration that writes each local player's own-seat lobby packs into
> that bucket. The existing B&B lobby also writes to the same bucket from the same device's seat.
>
> **Interpretation locked with the user (session 2026-09-23):** when the pack-battle ceremony completes
> on *this device*, only the local seat's own packs count to its `openedCards` bucket. Host → even-indexed
> packs; guest → odd-indexed packs; the odd tail pack (when the count is odd) is `seatForPack === 'both'`
> and counts to **both** seats' local buckets. The opponent's packs are visible on both screens but never
> touch the local player's collection.

## Required inputs

- Name/id: Pokémon Pack Rips / `rip` (internal feature inside `pokemon-pack-battle`; not a separate game in the registry)
- Loop:
  - `start` → **(RIP packs)** → `rip` → open solo packs (set + count + name) → results grid → **(Unlocked)**
    → `unlocked` (set + player) → back to `rip` → back to `start`
  - `rip` → "Open more packs" → reset solo open, back to the same form
  - `unlocked` → "Back to pack rip" → `rip`
  - Both pages have exit controls to `start`
- Win/loss: **none** — this is a solo collection feature, no scoring, no opponent, no wire sync
- Persisted shape: `AppConfig.openedCards: Record<string, string[]>` where the key is the lowercased,
  trimmed player name and the value is a deduplicated, **sorted** list of opened card ids for that player
- Card source for solo rip: `openBattlePacks(battleSetCards(), PACK_BATTLE_30C, packCount, rng)` with a
  fresh random seed, identical shape to the ceremony pack (6-slot, same rarity weights) — so a solo rip
  draws from the same 30C distribution
- Sets supported (for now): 30c only, via the shared `listSets()` + `PACK_BATTLE_30C` — the rip component
  reuses the same set registry, so future sets work without a rip-specific change
- Rarity percentages: identical to `PACK_BATTLE_30C` (energy / common / common / pikachu-IR / common-or-better
  ladder / uncommon-or-better ladder with the same weights) — no new weights, no new slots
- Unlocked page display:
  - A set selector (reuses `packBattle.setLabel`) and a player selector (population = `listPlayers()` over
    the persisted `openedCards` bucket)
  - For the chosen set+player: **only cards that the player has opened in that set are shown**, sorted by
    card number ascending
  - Cards not yet opened are **not rendered** ("hiding cards not yet been opened")
  - Each shown card renders `PokemonCard` with its translated rarity chip (no score chip — no scoring here)
- Lobby-game integration:
  - When the pack-battle ceremony completes on this device (`ceremonyComplete` flips true), derive the
    local seat's opened card ids from the ceremony's `battlePacks` array using `cardIdsForSeat(
    battlePacks, seatForPack, totalPacks, localRole)` and record them with `recordOpenedCards(displayName, ids)`
  - Only the local seat's packs: `seatForPack(packIndex, totalPacks) === localRole || === 'both'`
  - The opponent's packs are not recorded to the local player's bucket
  - **Deferred (not in 04.3, decided 2026-09-24):** the B&B lobby (`pokemon-bnb`) opens packs too, and a
    future `pokemon-bnb` pass will record that seat's ids with the same helper
    (`recordOpenedCards(bnbDisplayName, ids)`, same bucket, same dedupe). `PokemonBnbGame.tsx` is not
    touched in this feature.
  - `recordOpenedCards` is pure-dedupe-and-merge: it unions the new ids into the existing player list,
    re-sorts, and writes; opening the same card again does not duplicate it
- Keybinds: none new for this feature (buttons only; no Confirm/Skip wiring here). The existing pack-battle
  bindings stay the same.
- Highscore: not involved (no scores). The existing `pokemon-pack-battle` highscore bucket is unchanged.
- Credit: inspiration row for the collection idea if it is a new player-visible inspiration; if it is an

## Surfaces and behaviour

### RIP page (solo pack rip)

1. Header: `packBattle.ripTitle` / `packBattle.ripEyebrow`.
2. Player name input (defaults to `packBattle.defaultName`, trimmed, maxLength 16) — this is the player
   whose collection the rip's opened cards will be recorded to.
3. Set selector (segmented, reuses `listSets()` + `packBattle.setLabel`), currently only 30c.
4. Pack-count stepper (1–18, same limits as the lobby stepper; reuses `PACK_BATTLE_LIMITS` semantics and
   the translated `packBattle.decrease`/`packBattle.increase` labels).
5. Primary button "Open packs" (translation key `packBattle.ripOpen`):
   - On click, roll a fresh random seed locally (no wire), derive `openBattlePacks(battleSetCards(), PACK_BATTLE_30C, count, rng)`,
     record the resulting card ids to `recordOpenedCards(playerNameLower, ids)`, and show the results grid.
   - The results grid shows every opened card face-up with its translated rarity chip (reuses the same
     rarity keys the ceremony uses: `packBattle.rarityCommon/Uncommon/Rare/UltraRare/IllustrationRare`).
   - Show a short line: how many packs, how many cards, and a `packBattle.collectionSaved` notice
     (`{player}` = the trimmed display name used for the rip).
   - Buttons: **(Unlocked)** → `unlocked` page for the same set + player; **Open more packs** → reset
     the solo open back to the form (keeps the player name and set for convenience); **Back to pack battle**
     → `start`.
6. While the solo open has not been triggered, the results grid is absent and only the form is shown.
7. The seed is session-only (not persisted) — re-opening the RIP page gives a fresh solo open.
### Unlocked page (collection browser)

1. Header: `packBattle.unlockedTitle` / `packBattle.unlockedEyebrow`.
2. Set selector (segmented, reuses `listSets()` + `packBattle.setLabel`).
3. Player selector (a `<select>` populated from `listPlayers()` — only players who have at least one
   opened card in the persisted bucket appear; if none, show `packBattle.unlockedNoPlayers`).
4. Cards grid: **only cards the chosen player has opened in the chosen set**, sorted by card number
   ascending. Each card renders `PokemonCard` with its translated rarity chip. Cards not opened are
   **not rendered** (no locked/placeholder tile in v1 — the set is simply partially empty).
5. If the chosen player has opened zero cards in the chosen set: a short `packBattle.unlockedEmpty` line.
6. Buttons: **Back to pack rip** → `rip`; **Back to pack battle** → `start`.
7. Selection is local only (set + player); no persistence of the selector.

### Start shell "(RIP packs)" button

- Added on the pack-battle start shell, inside the existing `.ppb-actions` row (or a small adjacent row
  if the shell already has both create/join buttons there), labelled `packBattle.rip`.
- On click: `setView('rip')` (the RIP page is inside the pack-battle game component, so no extra routing).
- The start shell continues to also show the lobby create/join buttons and the existing highscore table.

### Lobby-game integration (pack-battle ceremony)

When `ceremonyComplete` becomes true on this device, record the local seat's opened cards:
- `localRole = role === 'guest' ? 'guest' : 'host'`
- `localIds = cardIdsForSeat(battlePacks, seatForPack, totalPacks, localRole)` — the ids from every
  pack whose owner is `localRole` or `'both'`, in pack order
- `recordOpenedCards(displayName, localIds)` — union + dedupe + sort, persisted under the trimmed display name
- Show a transient `packBattle.collectionSaved` notice (`{player}` = displayName) once per ceremony completion
- The opponent's packs are not recorded to the local player's bucket (by construction of `cardIdsForSeat`)
- If `displayName` is empty/trim-to-empty, fall back to `packBattle.defaultName` for the bucket key

### B&B lobby integration (same bucket, same device) — DEFERRED, not in 04.3

**Decided with the user 2026-09-24:** 04.3 ships the `pokemon-pack-battle` coding flow only.
`pokemon-bnb` is not modified (its bugs are handled in a future `pokemon-bnb` pass), so the pack-battle
ceremony is the only writer of the `openedCards` bucket here. Kept for the later pass: when the B&B lobby
ceremony on this device completes and the local seat marks `openingReady`, record that seat's opened ids
into the **same** `openedCards` bucket:
- `bnbLocalIds = openedCards.map((o) => o.card.id)` from the B&B memo (all cards the local seat saw in
  the lobby ceremony)
- `recordOpenedCards(bnbDisplayName, bnbLocalIds)` — same function, same bucket, same dedupe semantics
- Only the local seat's lobby cards count; this is the local device's own ceremony, so "opposing players'
  opened cards do not count" is automatically satisfied (we do not read the opponent's lobby cards here)
- This is a thin call placed next to `markOpeningReady`'s existing side-effect path in the B&B game, not a
  protocol change



## Persistence shape (CP1 detail)

```
AppConfig
└── openedCards: Record<string, string[]>   // key = lowercased trimmed player name
                                            // value = deduplicated, sorted opened card ids for that player
                                            // default seed = {}
```

- `mergeConfig` deep-merges `openedCards` (a plain object) so stored per-player lists survive into the
  default shape; new players added at runtime appear under their name.
- `recordOpenedCards(name, ids)`:
  - `key = name.trim().toLowerCase()`
  - `existing = readConfig().openedCards[key] ?? []`
  - `next = Array.from(new Set([...existing, ...ids]))` then `.sort()`
  - `updateConfig((c) => ({ ...c, openedCards: { ...c.openedCards, [key]: next } }))`
- `readOpenedCards(name)` → the sorted id list for that player (or `[]`), from `readConfig().openedCards`
- `listPlayers()` → `Object.keys(readConfig().openedCards)` (the keys are already lowercased player names)
- `hasCard(name, cardId)` → `readOpenedCards(name).includes(cardId)`
- `cardIdsForSeat(battlePacks, seatForPack, totalPacks, seat)` → ids from packs where
  `seatForPack(packIndex, totalPacks) === seat || === 'both'`

Do NOT introduce any other storage key. The single key stays `flash-games.config`.

## State machine (new views)

```
start ──(RIP packs)──> rip
rip  ──(Unlocked)──>   unlocked
rip  ──(Open more packs)──> rip   (reset solo open, same form)
rip  ──(Back to pack battle)──> start
unlocked ──(Back to pack rip)──> rip
unlocked ──(Back to pack battle)──> start
```

No dead ends: both new views leaveable to `rip` and to `start`.
