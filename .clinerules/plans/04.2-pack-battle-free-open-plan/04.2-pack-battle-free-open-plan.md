# Implementation Plan — Pokémon Pack Battle: free-order own-pack opening (04.2)

> **Status: ACTIVE — scheduled by the user 2026-09-24.** Supersedes the linear
> v2 ceremony (`pair-open {pairIndex}` / `card-reveal {pairIndex, cardIndex}`,
> one round = one pack per seat, mirrored lockstep reveal). The 04.1 plan's
> "Deferred: protocol v3" note now points here as the live plan.

## Goal

Let each player open their **own packs**, in any pack order, with every action still mirrored to the other
screen — replacing the current linear "one round = one pack per seat, revealed in lockstep" cursor. Each seat
works one focused pack at a time. Opening a pack places all six cards in one overlapping face-down stack; each
click raises the front unrevealed card and flips it face-up. After all six cards are revealed, the pack stays
complete until that player explicitly starts another owned pack.

## Required inputs (user — locked)

- Each player opens their **own** packs only and may choose their next owned pack in any order. Within an opened
  pack, cards reveal strictly one at a time from front to back in deterministic seeded slot order (0 through 5).
- It **still shows on both screens**: if player 1 opens their pack 1, player 1's pack 1 opens on player 2's
  screen too; if player 2 opens pack 4, that pack 4 opens on player 1's screen too.
- Both seats keep playing simultaneously — no shared round cursor, no waiting for the other seat's turn.
- One focused pack is shown at a time per seat. Its six cards are stacked face-down together, not laid out as
  a grid. Only the front unrevealed card is actionable; offset edges are visual depth cues, not separate
  card-selection targets.
- Clicking the stack raises its front unrevealed card, then uses the shared `PokemonCard` flip animation to turn
  that exact card face-up. The revealed card then moves behind the remaining hidden stack rather than occupying
  a separate grid slot. The next click raises the next card in the fixed seeded order.
- When all six cards are revealed, the ceremony does not auto-advance. The completed stack remains visible
  until the owning player explicitly starts/selects their next unopened pack.
- Reveal-all remains available while hidden cards remain, presenting the remaining front cards one at a time
  through the same raise-and-flip animation without changing their fixed order.

## Flow checks (02-diagram-flow-checks)

- **State machine**: `opening` stays one view; completion still gates `summary` behind the click gate

- **Component flow**: game logic stays in `pokemon-pack-battle/`; P2P I/O still funnels through

- **Localization flow**: new/changed copy goes through `en/ms/zh.json` + `PackBattleTranslationKey` union
  first (01 + 02 localization flow), parity en==ms==zh before rendering it.

## Design constants

- Protocol **v3**: per-pack `pack-open {packIndex}` + `card-reveal {packIndex, cardIndex}` replace the
  round-based `pair-open` / `card-reveal {pairIndex, cardIndex}`; plus idempotent `ceremony-sync`
  `{ opened: number[], revealed: Record<number, number[]> }` (union-merge snapshot) for re-dial catch-up.
  Bump `PACK_BATTLE_PROTOCOL_VERSION` to 3 — the version guard already rejects mismatched builds,
  so v2↔v3 cross-play fails closed with `errorVersion`.
- State: `{pairIndex, cardIndex, opened}` cursor → per-pack map keyed by pack index:
  `packs: Record<packIndex, { opened: boolean, revealed: boolean[] }>` (6 flags), plus a derived focused pack
  per seat (the most recently opened incomplete owned pack; `null` only when that seat is done). Within each
  pack, `revealCard` accepts only the lowest-index unrevealed slot, enforcing the deterministic seeded order.
  The old `revealedAnim` cursor cascade retires. Card state is authoritative immediately; CP4 may keep a
  short **presentation-only** reveal queue for reveal-all so hidden cards are mounted face-down in sequence,
  while totals and protocol state use the received `revealed` flags immediately.
- Ownership: `seatForPack(packIndex, totalPacks)` gates **clicks** (host = even, guest = odd,
  odd tail `both` = either seat; first click wins, union-merged). **Rendering is ungated** — every
  opened/revealed pack shows on both screens. Opening a pack selects it as that seat's focused pack; after
  card six the focus is retained as a completed pack until an explicit next-pack action sends a new `pack-open`.
- Scoring unchanged (identity scoring, Pikachu IR = 0); totals sum revealed flags per pack instead of the
  cursor prefix. Completion = every pack opened AND all 6 flags set on every pack.
- Layout: two simultaneous seat lanes (host left, guest right; one full column if an odd tail is shared), but
  **one focused pack stack per lane**, never the old pair/round view. Each lane also has a compact owned-pack
  selector/list so the player explicitly chooses the next sealed pack after the current six finish. Pack
  progress is "card N of 6" plus per-seat pack progress, not rounds. 960×540 embed, `min(100%, 960px)` caps,
  mobile-landscape `100dvh` pattern, ≤520px portrait stacking (per 01).
- Stack interaction: all six cards occupy the same footprint with small z/translate offsets; only the front
  card's full face is visible. The stack exposes one real button/focus target, never one target per offset edge.
  Activating it reveals only the lowest-index unrevealed slot, raises that card to the front, then clears its
  `faceDown` flag; the shared `.pkm-card-flipper` performs the face-up rotation and reduced-motion fallback.
  The revealed card returns behind the remaining hidden stack. Stack transforms and the reveal-all presentation
  queue live only in the pack-battle component; network/scoring state never waits for animation completion.
- Copy: `packProgress` ("Round {current} of {total}"), `packsLeft`, `ceremonyOpenHint`,
  `ceremonyRevealHint`, `actionRevealPack` ("Reveal both packs"), `actionNextPack`, `tutorialOpen` change
  meaning (no rounds, no lockstep, explicit per-seat focused pack and next-pack selection). Old round keys are
  retired or reworded in the same locale pass — never leave a dead key in the dicts.
- The rip page (`PokemonPackRip`) is untouched — it is the reference UX, not a consumer.
