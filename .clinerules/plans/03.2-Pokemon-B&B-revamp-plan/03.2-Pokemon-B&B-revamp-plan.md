### Locked product decisions

- Deck size is __exactly 40 cards__, no more and no fewer.
- Non-Energy cards must come from cards opened by the player.
- Energy cards may be added from every available Energy type.
- Energy cards are a separate construction pool and are not constrained by opened-card copy counts.
- The total of __40 includes Energy cards__.
- Prize cards are __not part of the 40-card deck total__.
- Prize-card setting is configurable to exactly __4 or 6__, with __4 as the default__.
- Prize cards are taken from the configured 40-card deck during battle setup.
- The battle follows the supplied Draw, Main Turn, Attack/Pass, and Between-Turns phases.
- Both player sides use the same board structure; the opponent side uses the same layout flipped.
- Pack reveals follow the shipped `PackStack` pattern.
- No new persisted `AppConfig` field is planned.
- The B\&B peer protocol will be version-bumped because the Prize-card rule and deck format become semantically incompatible with version 1 peers.
- One implementation checkpoint will be completed per session turn, followed by `npm run build` and `npm run lint`.

## CP3 — Battle setup state machine and explicit start-of-game flow

The supplied setup flow is adapted as follows for B\&B:

1. Shuffle each 40-card deck deterministically.
2. Flip the opening coin before looking at hands.
3. First/second choice occurs before opening-hand reveal.
4. Both players draw seven cards.
5. If no Basic Pokémon exists, resolve a Mulligan.
6. Each player explicitly chooses one Basic as Active.
7. Each player explicitly chooses up to five Basic Pokémon for Bench.
8. Set the configured 4 or 6 Prize cards.
9. Reveal Active and Benched Pokémon simultaneously.
10. Begin the chosen first player’s Draw Phase.

The reference says “shuffle your 60-card deck”; the revamp replaces 60 with the locked B\&B deck size of 40.

### Engine state

Extend the battle state with explicit setup ownership and readiness, for example:

- setup phase separate from the first Draw Phase;
- Active selection readiness per side;
- Bench selection readiness per side;
- setup completion only after both sides are ready;
- first-turn restrictions based on the chosen first player;
- setup placement tracking for first-turn evolution restrictions.

`setupBattle` should create shuffled decks, draw seven, resolve automated mulligans, seed the coin flip, and leave Active/Bench selection pending rather than randomly selecting them.

### Setup actions

Add typed actions such as:

- `setupActive { handIndex }`
- `setupBench { handIndexes }`
- `finishSetup`

The exact action names are finalized against the existing engine conventions during CP3.

Validation must enforce:

- only a Basic Pokémon may become Active;
- selected card leaves the hand;
- only Basic Pokémon may be placed on Bench;
- no more than five Bench Pokémon;
- no duplicate placement;
- no setup action after setup is complete;
- both sides must finish before setup completes;
- Prize cards are not visible in snapshots;
- opponent’s hand and deck remain private.

### Mulligan behavior

The current automated Mulligan may be retained internally, but the flow must record and expose:

- whether a Mulligan occurred;
- how many times it occurred;
- the opponent’s extra-card penalty;
- deterministic ordering of both players’ Mulligans.

The extra penalty cards are drawn after Prize setup, as required by the source rule.

### Prize setup

Replace the fixed `PRIZE_COUNT` side initialization with the configured 4/6 value.

The engine must:

- take exactly the configured number of cards from the shuffled deck;
- leave them face down;
- track `prizeCards` consistently in `BattleState`;
- use the same configured total for snapshots, victory, and UI;
- not reduce the player’s required constructed deck below 40.

__Validation:__

## CP4 — Draw, Main Turn, Attack/Pass, and Between-Turns state machine

### Turn phases

Replace the current coarse `draw | main | end` lifecycle with the supplied sequence:

- `setup`
- `draw`
- `main`
- `attack`
- `betweenTurns`

The Attack Phase is the final turn phase. Both __Attack__ and __Pass__ end the turn.

The UI should reflect the current phase, but it must not expose a phase that permits out-of-order actions.

### Draw Phase

At the start of every turn:

- reset that player’s per-turn limits;
- adopt setup Pokémon into the current-turn tracking;
- mark special turn-one restrictions;
- draw exactly one card;
- if drawing is impossible, immediately end the match as a Deck Out;
- transition to Main Turn only after a successful draw.

No user-selected “draw” action is required unless the existing network architecture needs an explicit setup acknowledgement. The phase itself is authoritative and idempotent.

### Main Turn actions

Implement actions in any order:

#### Unlimited actions

- Play Basic Pokémon to an empty Bench slot.
- Evolve a matching Pokémon.
- Play Item cards.
- Attach a Pokémon Tool to a Pokémon without one.
- Use an eligible ability that states it may be used during the owner’s turn.

#### Once-per-turn actions

- Attach one Energy card to one Pokémon in play.
- Play one Supporter.
- Play one Stadium.
- Retreat once.

#### Additional rules

- No evolution:

  - on the first turn a Pokémon is in play;
  - during Turn 1 of the game.

- The first player cannot play a Supporter on their first turn.

- The first player cannot attack on their first turn.

- A Stadium with the same card name already in play cannot be played.

- Item and Tool support depends on the current data/engine model; any unavailable card category is logged as unsupported rather than simulated.

- Asleep and Paralyzed prevent attack and retreat.

- Confused permits an attack attempt but requires a coin flip.

### Retreat

Revise retreat state from a Pokémon-only stamp into a side/turn restriction:

- no more than one retreat per player per turn;
- pay the exact retreat cost from attached Energy;
- select a valid benched replacement;
- cannot retreat while Asleep or Paralyzed;
- cannot retreat from an empty Bench.

### Pass

Add an explicit `passTurn` action or rename the existing end-turn action according to the locked rules. Passing:

- is allowed during the Attack Phase;
- performs no attack damage;
- ends the turn;
- proceeds through Between-Turns;
- starts the opponent’s Draw Phase.

### Between-Turns

Rewrite `applyCheckup` as a strict phase with the supplied order:

1. Resolve Special Conditions.
2. Resolve between-turn Abilities/Trainers/Stadiums.
3. Check all Pokémon for Knock Outs.
4. Complete the next player’s turn transition.

Special Conditions must be processed as effect types in the required global order, not per player:

- resolve all Poison first;
- then all Burn;
- then all Asleep;
- then Paralysis recovery.

This matters when both Active Pokémon carry different conditions.

### Damage and KOs

After all status and between-turn effects resolve:

- check both sides for KOs;
- move each KO’d Active and all attached cards to discard;
- award the corresponding Prize;
- support simultaneous KOs;
- record independent promotion requirements for both sides;
- resolve promotions with the next player choosing first, as supplied.

Promotion-gate state must therefore hold more than one pending player or an ordered queue. It must not overwrite the first KO with the second.

__Validation:__

- Draw/deck-out.
- Out-of-phase action rejection.
- Any-order Main Turn actions.
- Every once-per-turn limit.
- First-turn attack/Supporter/evolution restrictions.
- Pokémon entered-to-Bench evolution restriction.
- Pass flow.
- Condition-order trace.
- Simultaneous KOs.
- Ordered promotion.
- Snapshot roundtrip and host/guest agreement.
- Build and lint.

## CP5 — Ability triggers, attack requirements, and deterministic resolution

### Ability model

Add an explicit ability action and trigger metadata.

Abilities are not attacks and do not consume Energy.

For each supported ability, determine from card text:

- owner-only versus shared trigger;
- during-turn versus passive versus between-turn trigger;
- once per ability user per turn;
- whether multiple copies can use it independently;
- source and target selection;
- required coin flips, counters, draws, damage, or movement;
- whether a Neutralization Zone or comparable effect suppresses it.

The supplied rule says special conditions usually do not prevent abilities, so the engine must not automatically block ability use for Asleep, Confused, or Paralyzed. Only explicit card/effect text may do so.

The current `abilityUsedTurn` field is insufficient for multiple ability sources. Replace or supplement it with stable per-Pokémon/per-ability usage records.

### Ability coverage

Create a deterministic effect registry rather than expanding loose text-matching indefinitely.

For every 30C ability:

- classify as supported or explicitly unsupported;
- add a stable technical effect ID;
- map the card to that ID;
- preserve original card text as data;
- never apply a guessed effect;
- log unsupported behavior using translated UI copy.

### Attack requirements

For every attack:

- only the Active Pokémon may attack;
- exact typed Energy must match;
- Colorless Energy cost accepts any attached Energy type;
- a specific Energy symbol accepts only its matching Energy;
- insufficient Energy rejects before effects mutate state;
- first player cannot attack on Turn 1;
- Asleep/Paralyzed reject;
- Confused performs the supplied seeded coin flip.

### Attack resolution order

Implement:

1. Read and validate immediate requirements.
2. Start with printed base damage.
3. Apply attacking-Pokémon damage modifiers.
4. Apply Weakness.
5. Apply Resistance.
6. Place final damage.
7. Resolve post-damage effects.
8. resolve KOs and prizes.
9. end the turn.

The existing weakness parser and resistance fallback should be retained where correct, but verified against the actual 30C data.

### Confusion

Follow the supplied rule exactly:

- Heads: attack resolves normally.
- Tails: attack does not resolve and the attacking Pokémon receives 30 damage.
- The turn still ends.
- A self-KO follows the promotion/victory path.

### Effect safety

Any unsupported or partially understood attack clause must not be applied speculatively. A partial parser must not apply a recognized fragment while ignoring an unresolved condition that changes its meaning.

__Validation:__

- Typed and Colorless Energy payment.
- First-turn attack rejection.
- Active-only attack.
- Asleep/Paralyzed rejection.
- Both Confusion outcomes.
- Weakness and resistance ordering.
- Damage-modifier ordering.
- KO and simultaneous-KO behavior.
- Ability per-copy and once-per-name restrictions.
- Every supported card effect ID.
- Unsupported-effect coverage report.
- Build and lint.

Create a co-located `BattleBoard.tsx` and `BattleBoard.css` instead of expanding the already large `PokemonBnbGame.tsx`.

The board follows `board-state.md`:

- one shared Stadium zone centered between the two sides;

- opponent side at the top;

- player side at the bottom;

- each side uses the same zone layout, with the opponent’s side vertically flipped;

- each side contains:

  - Active Pokémon;
  - Bench capacity up to five;
  - Prize cards;
  - Deck;
  - Discard pile;
  - hand treatment appropriate to visibility.

The same reusable side component renders both seats. Opponent orientation changes CSS transform/layout direction, not a separate divergent board implementation.

### Zone behavior

- Stadium: one shared face-up card or empty slot.

- Active: public, with HP, damage, conditions, and attachments.

- Bench: public, maximum five.

- Prize: hidden and shown as face-down placeholders plus remaining count.

- Deck: hidden and shown as face-down stack plus count.

- Discard: public face-up cards or compact stack.

- Hand:

  - owner may see private cards;
  - opponent sees only a count;
  - snapshots continue to enforce privacy.

### Attachments

Revise the in-play Pokémon model to represent attached cards by category rather than Energy-only:

- Energy cards;
- Pokémon Tools;
- future attachment categories when supported.

Attached cards remain publicly visible where the rules require visibility and move to Discard with a KO’d Pokémon.

Stadium ownership/state must be added because the current `stadiumPlayedTurn` flag is only a per-turn restriction and cannot represent the shared Stadium in play.

### Responsive layout

  - stack or compact zones without requiring horizontal scrolling.
