## Locked decisions and source rules

The five files in this directory are locked inputs: `actions-per-turn.md`, `between-turns.md`,
`board-state.md`, `pokemon-ability-and-attacks.md`, and `start-of-game.md`. This is an active
follow-up to the completed `03-Pokemon-B&B-plan` and `03.1-Pokemon-CP8-plan`; completed work is not
reopened without a confirmed conflict.

- Deck is exactly **40 cards**, including Energy; no more and no fewer.
- Non-Energy cards come from the player’s opened pool and respect its copies.
- Energy is a separate construction pool with every available basic Energy type and unlimited copies.
- Prize cards are **not** part of the 40-card construction total; setup takes the configured 4 or 6
  from that deck. The lobby choice is exactly 4 or 6, default 4.
- Draw → Main Turn → Attack/Pass → Between-Turns is the required turn flow.
- Both sides use the same board; the opponent side is flipped.
- B&B reveals follow the shipped `PackStack` behavior.
- No new `AppConfig` field/storage key is planned; any required schema change must be documented first.
- B&B protocol becomes version 2 because version-1 peers cannot safely share the revised rules.

## Shared implementation gates

Each implementation CP must preserve the project rules: pure rules under `game-core`, React orchestration
isolated in the game component, translated player-facing copy in en/ms/zh, co-located CSS, 960×540
16:9 with no horizontal scrolling, and clean effect/resource handling. After each CP, update the focused
plan and this index together, run `npm run build` and `npm run lint`, and stop for review.

## Scope boundary

The coordinator does not repeat the detailed implementation, rule, or validation steps from CP1–CP10.
Those details live in the linked focused checkpoint plans. Any change to persisted schema, state-machine
flow, registry wiring, or diagrams must be recorded in the relevant focused plan and the Mermaid diagrams
before implementation proceeds.
