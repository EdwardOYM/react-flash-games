## Scope outcome: validation, not re-implementation

An audit showed essentially all of CP9's machinery was already built by the earlier `03` plan
(host-authoritative `battle-action`/`battle-snapshot`, per-seat `toSnapshot`, turn timer + host
`applyTimeout`, disconnect banner + re-`hello` replay, rematch via a fresh `lobby-start`, results
routing, and the `resultRecordedRef` one-shot highscore guard). Per the coordinator's rule that
completed work is not reopened without a confirmed conflict, this checkpoint **added the
verification harness that the revamped behaviour had never been exercised against**. No product
code changed: the harness found no product defect, only two mistakes in my own test helper.

## What was verified

- `scripts/cp9-assertions.ts` (throwaway, deleted after the run) — **19 assertions passed**:
  - **Protocol v2**: `hello`/`hello-ack` at v1 are rejected; every one of the ten wire kinds is
    guarded; unknown/kindless/non-object payloads are dropped; a `lobby-update` with an illegal
    Prize count (5) or pack/timer value is rejected on the wire; `deck-ready` accepts only exactly
    40 non-empty ids; `battle-action` must name a real seat, so a forged seat is rejected.
  - **Host authority**: a guest intent round-trips the real wire payload and is applied on the host
    state; the same intent is rejected when it is not the guest's turn, and a rejected intent does
    not mutate the host state.
  - **Snapshot privacy**: each seat receives its own hand and never the other seat's; a rebuilt
    snapshot is `viewOnly` and refuses every action; hidden deck/prize/hand zones are nameless
    placeholders.
  - **Snapshot idempotence**: `toSnapshot → applySnapshot → toSnapshot` is byte-identical for both
    seats, which is what makes a re-`hello` replay safe.
  - **Timeout**: expires the turn on the host, is an identity no-op when the timer is `0`, and never
    fires on a finished match.
  - **Rematch**: a new seed opens a genuinely different pool while the same seed still reproduces
    the identical pool (so both seats stay in step).
  - **Results**: the configured 4- and 6-Prize totals both reach the match, and each of
    `prizes` / `deck-out` / `no-pokemon` survives the snapshot.
  - **Session-only state**: the `AppConfig` shape is still exactly
    `highscores / openedCards / settings / version` — this revamp added no persisted field.
  - **Record-once**: `recordMatchWin` has exactly one call site, wrapped by the `resultRecordedRef`
    guard, and the guard is re-armed by `resetMatchState` so a rematch records again.
  - **Keybindings**: `pokemon-confirm` / `pokemon-skip` are still read from config and `keybindings`
    is still a persisted settings map.
- en/ms/zh parity: **614 keys**, 0 missing (no new copy was needed this checkpoint).
- `npm run build` passed; `npm run lint` 0 warnings / 0 errors.

## Defects found

- **None in product code.** The harness surfaced two mistakes in my own throwaway deck-builder helper
  (it padded past the opened copy limit, and hard-coded a 16-Energy split that a 20-card pool cannot
  fill). Both were harness-only and were fixed by deriving the Energy count from the pool.

## Notes

- The real finding worth carrying forward: a **1-pack lobby opens only ~20 cards**, so a legal
  40-card deck is reachable only because Energy is an unlimited construction pool. The deck builder
  already tops up with Energy, so this is correct — but it means `minPacks: 1` is playable *by virtue
  of* the Energy catalog, not because the pool alone can fill a deck.
- No persistence change, so the database-schema diagram needs no edit. The architecture-flow diagram
  still needs its CP1–CP9 revamp notes, which CP10 owns.
