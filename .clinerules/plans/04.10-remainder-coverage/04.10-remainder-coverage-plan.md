# Implementation Plan — 04.10: the remaining card text (04.10)

> **Checkpoint protocol** (from `05-agent-discipline.md`): run ONE checkpoint per session turn. After each
> checkpoint run the narrowest relevant validation, report *files + behaviour + result*, then STOP and wait
> for "next".
>
> **Scope:** `pokemon-bnb`'s engine only, continuing 04.9. Not a new game, no persistence, no protocol
> change unless a checkpoint below says so explicitly.

## The measurement this plan is built on (CP0, not an estimate)

04.9 ended at **124 of 154 attack texts parsing fully** (30 unsupported, 25 unique) and **5 of 10**
passive Ability texts. This plan re-measured both by running the real parser over every card in
`src/assets/pokemon-bnb/sets/30c/cards.json`, so every row below is an observation, not a guess.

**25 unique unsupported attack texts / 30 instances. 5 unique unsupported passive texts / 8 instances.**

## Progress

- [x] **CP0 — this plan, written from a measurement.** A throwaway probe ran the real parser over every
      card in the set and dumped each unsupported text with the exact sentences that block it; the probe
      was deleted after the run. **Gate: `npm run lint`.**
- [ ] **CP1 — Groups A, B, J: the discard/deck picks 04.9 built the seam for.** Five texts
      (081 Gimmighoul, 048, 063, 103, 109/156) and the biggest structural win available: 04.9 CP4 made a
      choice resolve N times and CP3 made it read a live zone, so "put up to 2 Basic Energy from your
      discard into your hand" is a **target rule**, not a new mechanism. **Gate: build + lint + harness
      proving a discard pick can take 0, 1 or 2 cards, that duplicates are handled, and that the Bench cap
      is enforced for 109/156.**
- [ ] **CP2 — Group D + 087, and Group F (the coin families).** 087 is one more `DurationEffect`
      (`lessDamageDealt` — it changes the ATTACKER's output, the mirror of 04.9 CP6's 028). 099/125 need a
      parsed coin count the existing `coinFlipDamage` already tracks internally. **Gate: harness proving
      the reduction applies before Weakness, and that "for each heads" fires exactly N times.**
- [ ] **CP3 — Group E: "during your opponent's LAST turn" memory. The first new engine state in two
      plans.** 005/091/085/138 all need to know what happened *last turn*, which means per-Pokémon fields
      written at the end of a turn and read at the start of the next. **This touches `BattleState` AND
      `Snapshot`** and needs its own wire + idempotence harness. **Gate: harness proving the memory is
      written exactly once per turn, cleared before it is read again (never compounding), survives a
      snapshot round trip, and cannot be read for the current turn's own damage.**
- [ ] **CP4 — Group C: attach Energy FROM the deck (007, 042).** A search followed by an attach, so it
      composes 04.8 CP3-B with `attachEnergy`. 042's cap is a **coin count**, which is the one place a
      search's `max` is not a printed number. **Gate: harness proving the attached Energy goes to the
      RIGHT Pokémon, that the once-per-turn Energy limit is respected, and that 042's cap equals the
      heads actually flipped (both 0 and a run of heads).**
- [ ] **CP5 — Group H + I: "attach ANY number" (054/150) and shuffle-self-into-deck (073/136).** Both are
      *player-directed* rather than automatic, so both need a choice kind with a per-card target pick.

## Explicitly OUT of scope, and why

- **026 / 116 (opponent-hand reveal) stay BLOCKED.** This is the one product decision 04.9 refused to
  make unilaterally, and nothing has changed to unblock it: a seat's snapshot still never carries the
  other seat's hand, and 04.8 CP6's invariant is load-bearing for every pick already shipped. The
  options are still (a) leave both unsupported, (b) a **player-consent toggle in the lobby**, or
  (c) an out-of-band reveal to the acting player only, which needs a new `NetMessage` and a host-side
  send that is not part of the snapshot. **This plan does not choose.** Group L stays unimplemented until
  a human picks one, and the coverage figure below does not count it as reachable.
- **069 Espeon's devolve** is deferred for a *data* reason, not a scheduling one: 30C carries **zero
  `evolvesFrom` links** (verified in 04.9), so "the highest Stage Evolution card" has no answer the
  engine can derive. Implementing it means inventing a rule — which is a product decision.
- **No `AppConfig` or storage change.** Everything here is per-match `BattleState` (and, for the wire
  checkpoints, `Snapshot`). `default.config.json` and `src/config/index.ts` are not touched.
- **No protocol change** except if/when 026/116 is unblocked.

## Why the ordering is what it is

Ordered by **mechanism needed, ascending**, deliberately NOT by instances covered:

1. **CP1** reuses two seams 04.9 already built and proven (live-zone picks, N-pick resolution). It should
   be the cheapest real coverage in the plan.
2. **CP2** adds one effect kind and reads an existing coin count.
3. **CP3** is the first checkpoint in a long time that adds *per-turn memory*. It is placed **after** the
   cheap work precisely because it is the first thing that can go subtly wrong, and it is also the one
   that most needs a browser to trust.
4. **CP4–CP5** compose existing mechanics but in new orders (search→attach, player-directed multi-attach).
5. **CP6** replaces the parser's splitter — the single highest-risk change in the plan, because it can
   regress *already-working* clauses. It is late on purpose; if it lands, the whole 124-text baseline
   must be re-measured, not just the two new ones.
6. **CP7–CP8** are the rules questions.

## Coverage this plan could reach

If every checkpoint lands: **25 → 0 unique unsupported attack texts** and **5 → 0** passive texts, i.e.

## The engine's standard, restated for this plan

**A wrong effect is worse than a missing one.** Concretely, for every clause added here:

- the pattern is **anchored end-to-end**, and a near-miss assertion proves it does not fire on the
  neighbouring shape. Note 04.9 caught itself filing a real card as a near-miss **three times** — a
  "different energy type" text and a "different number" text are legitimate sibling cards, not
  near-misses, so each candidate is questioned before it is asserted;
- a clause that cannot be honoured **falls through to `unsupported`**, never applies partially;
- anything that reads board state is asserted **with a control case that has the state absent**.
  04.9 found a green test suite **four separate times** that was really measuring a refused action
  (missing Energy, a deck-out, an Asleep attacker, Checkup poison) rather than the rule under test. That
  is the dominant failure mode of this engine and the thing to watch for in every checkpoint here.

## Hard rules

- 01-flash-game-builder: translated copy first (`en`/`ms`/`zh` + both unions, or a missing key renders);
  co-located CSS; the 960×540 cap and the landscape/portrait breakpoints.
- 02-diagram-flow-checks: **CP3 and CP7 may change the `Snapshot` shape** and must update
  `.github/diagram/architecture-flow.md` in the same change. Single storage key; no `AppConfig` change
  anywhere in 04.10.
- 04-terminal-commands: `git --no-pager`, non-interactive, `---done---` sentinels. **Never rewrite a
  source or plan file through PowerShell** — 04.9 CP5 corrupted `effects.ts` that way, mojibake in a
  **live regex**, and it was only caught because a reversibility check refused to run the bad fix.
- 05-agent-discipline: one checkpoint per turn; throwaway harnesses deleted after each run; harnesses
  live **outside `src/`** (04.9 CP4 learned that `tsconfig.app.json` includes `src`, so a harness in
  there breaks `npm run build`), bundled with the esbuild Vite already ships, because **this project has
  no test runner** and `npx vitest` hangs trying to fetch one.
